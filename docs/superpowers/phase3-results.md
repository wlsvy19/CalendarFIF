# ③ 단계 결과 (2026-11-13)

③ 단계(PC 바탕화면 앱)를 만들고 검토까지 끝냈다. 사용자가 자리를 비운 동안 진행했고 그동안 화면이 잠겨 있었다. 그래서 **실제 바탕화면에서 눌러 보고 입력해 본 사람은 아직 없다.** 이 문서는 무엇이 확인됐고 무엇이 남았는지, 사용자 대신 정한 것이 무엇인지 적은 것이다. 설계는 `specs/2026-11-13-pc-desktop-app-design.md`, 계획은 `plans/2026-11-13-phase3-desktop-app.md`에 있다.

## 지금 상태

- 브랜치 `phase-3-desktop-app`에 있고 GitHub에 올라가 있다. `main`에는 아직 합치지 않았다. 사용자가 실제 앱을 써 본 뒤에 합친다.
- 꾸린 앱이 `release\CalendarFIF-win32-x64\CalendarFIF.exe`에 있다(이 PC에만 있고 git에는 없다). 만들기만 했고 한 번도 실행하지 않았다.
- 웹앱의 달 넘기기 수정은 2026-11-13 23:47에 배포했다(사용자가 배포를 세션에 맡겼다). 아이폰에서는 앱을 닫았다가 다시 열면 새 화면이 적용된다.

## 확인된 것

| 무엇 | 어떻게 확인했나 |
|---|---|
| 규칙과 계산(배치, 공휴일, 음력, 설정, 창 자리, 단축키) | 단위 테스트 288개 |
| 웹앱의 달력이 이전과 같다 | 720개월의 달력 칸을 이전 코드와 비교해 모두 같았다. 화면 캡처도 이전과 같았다 |
| 창이 바탕화면 창에 붙고, 맨 아래에 있고, 작업 표시줄에 없다 | 앱이 실행 중에 Windows에 물어서 얻은 값 (시험 실행) |
| 창이 없어지거나 화면이 죽으면 다시 뜬다 | 시험 실행에서 일부러 없애고 죽여서 확인 |
| 동기화가 양쪽으로 된다 | 에뮬레이터에서 꾸린 앱으로 확인. 다른 기기의 변경이 약 0.3초, 앱의 변경이 약 0.2초 만에 반영 |
| 시험 실행이 Windows 시작 프로그램을 건드리지 않는다 | 등록 호출 횟수 0 |
| 꾸린 실제 앱의 내용물 | 실제 프로젝트 설정이 들어 있고, 에뮬레이터 설정과 `.env.local`, `.firebaserc`는 없다 |

## 아직 사람이 봐야 하는 것

저장소 `README.md`의 "직접 확인할 것" 14개 항목이 그 순서다. 그중 먼저 볼 것은 이렇다.

1. 로그인 화면에서 이메일 칸을 눌러 글자가 입력되는가.
2. 날짜를 더블클릭해 한글로 메모를 쓸 수 있는가. 편집을 끝내면 달력이 다른 창 뒤로 내려가는가.
3. 다른 창을 열면 달력이 그 뒤로 가려지고, Win+D를 눌러도 달력이 남는가.
4. 바탕화면 그림이 비쳐 보이는가. 글자가 읽히는가.
5. 아이폰과 서로 5초 안에 반영되는가.

## 진행하면서 정한 것

사용자에게 묻지 않고 정한 것을 정한 순서대로 적는다. 틀렸을 때의 비용을 함께 적는다.

1. ② 위젯보다 ③ PC 앱을 먼저 했고, 화면 시안 확인 없이 설계했다(사용자가 순서와 진행을 맡겼다). 틀렸다면 모양을 다시 손보거나 순서를 바꿔야 한다. 모양은 설정에서 바꿀 수 있다.
2. 창을 바탕화면에 붙이는 방식은 "바탕화면 창에 딸린 투명 창을 맨 아래에 두기"다. DesktopCal처럼 탐색기에 끼워 넣지 않는다. 틀렸다면 클릭할 때 창이 잠깐 올라올 수 있고, 탐색기가 다시 시작되면 창을 다시 만들어야 한다.
3. 계획 전체의 사전 점검이 도는 동안 첫 작업(웹앱 달 넘기기)을 먼저 시작했다. 비용은 없었다.
4. 화면과 메인 프로세스를 잇는 preload는 따로 한 파일로 빌드한다. 틀렸다면 빌드 단계 하나가 더 있다.
5. 맨 아래 자리를 확인하려고 창 목록(핸들, 소유자, 종류 이름)을 읽는 것은 허용했다. DesktopCal의 창도 목록에 들어 있다. DesktopCal 창에 신호를 보내거나 바꾸는 일은 하지 않는다. 비용 없음.
6. 사전 점검에서 나온 18건을 계획 문서에 반영했다. 설정 화면에 "계정" 쪽을 하나 더 둔 것과 "없음" 색을 세 줄에만 둔 것은 그대로 뒀다. 틀렸다면 해당 작업에서 검토가 한 번 더 든다.
7. 전체 월 배치에서는 다른 달의 날짜를 열면 그 달로 넘어간다(웹앱의 기존 동작 그대로). 나머지 세 배치에서는 보이는 쪽에 있으면 그대로 둔다. 틀렸다면 PC 앱의 전체 월 배치에서 회색 날짜를 누를 때 달이 넘어가는 것이 거슬릴 수 있다.
8. 자정이 지나면 "오늘"을 보고 있던 달력이 새 달로 따라 넘어간다. 웹앱에도 적용된다. 틀렸다면 월말 자정에 아이폰 화면이 저절로 바뀌는 것이 거슬릴 수 있다.
9. 메모·설정·로그인을 입력하는 동안에는 전역 단축키를 멈춘다. 틀렸다면 메모를 쓰는 중에는 "달력 숨기기" 단축키가 듣지 않는다.
10. 마지막 전체 검토에서 나온 중요한 것 4건과 작은 것 8건을 한 번에 고쳤다. 글 칸의 오른쪽 클릭 메뉴, 탐색기 재시작 때 창을 다시 만들지 않고 다시 붙이는 방식, 서명된 실행 파일과 전용 아이콘은 미뤘다. 틀렸다면 탐색기가 다시 시작될 때 열려 있던 편집 내용이 사라지고, 오른쪽 클릭 붙여넣기가 없고, 서명 없는 실행 파일을 회사 보안 프로그램이 막을 수 있다.
11. 시험 실행과 실제 실행 모두에서 Chromium의 "가려진 창 계산"을 끈다. 시험한 설정과 쓰는 설정을 같게 하려는 것이다. 틀렸다면 달력이 가려져 있을 때도 조금 더 그린다.
12. 시험의 약한 곳 몇 군데는 고치지 않고 적어만 두었다(아래 "미뤄 둔 것").
13. 브랜치를 `main`에 합치지 않고 두었다. 실제로 써 본 사람이 없기 때문이다. 틀렸다면 확인 뒤 합치는 단계가 하나 더 있다.

## 미뤄 둔 것

### 써 보면서 볼 것

- 칸의 오른쪽 클릭 메뉴가 다른 프로그램을 눌러도 남아 있을 수 있다. 달력의 다른 곳을 누르면 닫힌다.
- 밝은 바탕화면 그림이나 옅은 배경색 위에서는 빨간 날짜와 흰 글자가 약하게 보인다. 설정의 글꼴 및 색상 쪽에서 바꾼다.
- 메모나 로그인의 글 칸에는 오른쪽 클릭 메뉴가 없다. Ctrl+C와 Ctrl+V는 된다.
- 탐색기가 다시 시작되면 창을 새로 만든다. 그때 열려 있던 편집 화면의 글은 사라진다.
- 위치 및 크기를 조정할 때 가장자리를 화면 밖으로 끌면 반대쪽 가장자리가 움직인다.
- 완료 소리를 켜면 완료 표시를 하지 않은 저장에도 소리가 난다.
- 모니터 두 대에서의 자리 잡기는 계산 테스트로만 확인했다. 만드는 동안 모니터가 한 대만 연결되어 있었다.
- 실행 파일에 서명이 없다. 회사 PC의 보안 프로그램이 막으면 `npm run desktop`(개발 실행)으로 띄울 수 있다.

### 넣지 않은 DesktopCal 설정

유리 효과, 24절기, 최대 열 수, 편집 완료 단축키 바꾸기, 떠 있는 버튼, 날짜 선택과 월 선택 메뉴, 검색은 다음으로 미뤘다. 계정·동기화·VIP·업데이트·프록시·언어, 알림, 미완료 작업 자동 연기, 스티커 메모, 카운트다운 카드, 스킨과 배경 사진은 넣지 않았다.

### 코드와 테스트 정리

- 시험 실행의 `crashRecovered`는 이 PC에서 4.3~4.9초가 걸리는데 기준이 5초라서 가끔 거짓으로 실패할 수 있다. 기준을 8초로 올린다.
- "입력이 끝나면 맨 아래로 돌아간다"와 "편집 중 작업 표시줄 단추가 생기지 않는다"는 코드를 읽어서만 확인했다. 시험 실행의 값으로는 고장을 잡지 못한다.
- 창 메시지 처리 안에서 Windows 기능을 부르면 앱이 죽는다(실제로 겪고 고쳤다). `src/desktop/win32.ts`나 `window.ts`를 고친 뒤에는 `npm run desktop:smoke`를 여러 번 돌려 `nestedNativeCalls`가 0인지 본다.
- 음력 계산은 실행 환경에 한국 음력 달력이 없으면 양력으로 떨어지는데 이를 막는 확인이 없다(Electron과 Node 24에는 있다).
- 설정 파일(`settings.json`)이 더 새 버전의 것이면 모르는 칸을 버리고 저장한다.
- PC 앱 전용 코드가 웹 묶음에도 들어간다(실행되지는 않는다).
