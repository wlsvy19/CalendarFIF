## 한 일

"타이머"는 카운트다운(D-day)이다. 셀 설정은 넘버링, 셀 간격, 줄 간격, 완료 작업 두 가지, 알림 시각 표시, 효과음 둘(편집 완료 알람, 리마인드 알람)이다.
- **편집 화면:** 늘 펼쳐져 있던 배경색 줄을 없애고 아래에 도구 단추 넷(완료, 배경, 알림, 카운트다운)을 두었다. 배경은 색 상자에서 고르고 고른 색이 메모 칸 바탕에 보인다. 위쪽 띠에 그날의 알림과 카운트다운이 칩으로 보이고 누르면 고친다. 메모 칸은 도구 줄까지 채운다.
- **알림:** 글, 시각, 미리 알림(당일~일주일 전, 다섯 개까지), 반복(안 함, 매일, 근무일, 매주, 매달, 매년, 음력 매년)과 끝(계속, 날짜까지, 횟수), 완료. 삭제는 두 번 눌러야 한다.
  - 웹앱이 열려 있으면 화면 위쪽 상자와 소리로 알린다(아이폰은 화면을 한 번 누른 뒤부터 소리가 난다). 상자를 누르면 그 날짜를 연다(편집 중이면 고친 것을 저장하고 넘어간다).
  - PC 앱은 화면 오른쪽 아래에 맨 위로 뜨는 작은 창과 소리로 알린다. 창이 먼저 뜨고 소리는 그 뒤에 난다.
  - 아이폰에서 앱이 닫혀 있을 때는 Scriptable 위젯 스크립트가 돌 때마다 앞으로 7일의 알림을 가까운 것부터 48개까지 아이폰 알림으로 예약한다. 알림 시트의 `지금 예약`은 저장해 서버에 닿은 것을 확인한 뒤 `Scriptable 열기` 링크로 바뀌고, 그것을 누르면 바로 예약한다. 위젯에서 로그아웃하면 예약을 지운다.
  - 기기마다 울린다. 같은 기기에서 같은 알림은 한 번만 울린다(시각을 바꾸면 다시 울린다). 10분 넘게 늦은 것은 울리지 않는다.
- **카운트다운:** 유형(기본, 생일(나이), 기념일, 명절, 시험), 반복(안 함, 매년, 음력 매년), `달력 아래에 표시`. 달력 아래 줄에 "글 3일 남음", "오늘", "N일 지남"으로 가까운 순서로 보인다.
- **달력 칸:** 그날의 알림(종과 시각)과 카운트다운(모래시계, 생일은 케이크)을 메모 줄 앞에 적는다.
- **셀 설정:** 웹앱 설정에 `셀` 묶음(줄 머리, 셀 간격, 줄 간격, 완료된 작업 표시, 완료 작업 맨 아래로, 알림 시각 표시, 편집 완료 알람, 리마인드 알람). PC 앱의 셀 쪽에 알림 시각 표시와 리마인드 알람을 더했다.
- **자료와 동기화:** 알림과 카운트다운은 달 문서 밖의 새 문서 하나(`users/{uid}/data/events`)에 둔다. 옛 앱(PC 0.6.0, 옛 위젯)이 달 문서를 써도 닿지 않는다. 쓰기는 트랜잭션으로 서버 값과 비교해서 하므로, 오래된 오프라인 변경이 다른 기기의 새 변경을 덮거나 다른 기기에서 지운 항목을 되살리지 않는다. 보내지 못한 변경은 브라우저 저장소에 남았다가 연결되면 보낸다.
- **소리:** 직접 합성한다(완료, 차임, 벨). DesktopCal의 소리 파일은 쓰지 않았다.

## PC 앱 꾸리기

사용자가 `release`에 `CalendarFIF.exe` 파일 하나만 두라고 했다. 하려던 일: `electron-builder`(무료 빌드 도구, 개발용 의존성)로 지금의 앱 폴더를 한 파일짜리 실행 파일(portable)로 묶어 `release\CalendarFIF.exe`에 두고, 새 버전마다 그 파일을 바꾸고 옛 폴더를 지우며, Windows 시작 프로그램이 그 파일을 가리키게 한다. 한 파일짜리는 켤 때마다 안의 파일을 풀어서 몇 초 늦게 켜진다. 이 일을 맡긴 에이전트를 이 환경의 자동 권한 검사가 두 번 막았다("Unauthorized Access", 그다음 "Undermining Oversight"). 새 도구를 내려받아 설치하는 것, 사용자의 앱을 바꾸는 절차를 자동으로 만드는 것 중 어느 것이 걸렸는지는 모른다. 더 돌아가지 않고 사용자에게 묻는다. 작업 지시서는 git 밖의 `.superpowers/sdd/2026-11-15-memo-tools/task-13-brief.md`에 있었다(작업 공간을 지우기 전에 이 문서에 옮겨 적었다).

2026-11-16 아침 사용자가 "release 아래 CalendarFIF-win32-x64 이거 바로 놔서 0.0.1씩 증가하는거 없애라니까"라고 했다. 한 파일짜리가 아니라 지금의 앱 폴더를 버전 폴더 없이 `release` 바로 아래에 두라는 뜻으로 읽었다. 새 도구 없이 `scripts/pack-desktop.ts`만 고쳤다.

- `npm run desktop:pack`은 `build\pack-out\`에 꾸린 뒤 `release\CalendarFIF-win32-x64\`에 바꿔 넣는다. 쓰던 폴더는 `build\pack-replaced`로 옮겨 두었다가 새 것을 넣은 뒤 지운다. 새 것을 넣지 못하면 쓰던 것을 되돌린다(`swapDir`, 시험 2개). 백신이 막 만든 파일을 쥐고 있을 수 있어 폴더 옮기기는 1초 간격으로 다섯 번까지 한다.
- 그 자리의 앱이 켜져 있으면 바꿔 넣지 않고 멈춘다. 앱을 끄고 `npm run desktop:install`을 돌리면 바꿔 넣기만 한다. 꾸리는 1~2분 동안은 쓰던 앱이 켜져 있어도 된다.
- 바꿔 넣은 뒤 예전 방식의 버전 폴더를 지운다. 쓰이는 것(실행 중, Windows 시작 프로그램)은 남긴다.
- 확인: 에뮬레이터용으로 꾸려 시험 실행(`desktop:pack:check`)이 통과했다(`ok: true`, `nestedNativeCalls` 0). 실제 꾸리기로 0.8.0을 `release\CalendarFIF-win32-x64`에 넣었고 `release\0.6.1`은 지워졌다. `release\0.6.0`은 켜져 있고 시작 프로그램이 가리켜서 남았다.
- 켜져 있는 0.6.0을 프로세스 번호로 끄고 새 것을 켜는 일은 자동 권한 검사가 막았다("Destructive or Unwanted Actions"). 돌아가지 않고 사용자에게 맡겼다. 사용자는 "앱키 켜져 있으면, 너가 닫고 삭제 후 바뀐버전으로 다시 설치해"라고 했고, 그 뒤 세션이 0.6.0의 프로세스 4개를 번호로 끄고 새 앱을 켰다. 새 앱이 시작 프로그램을 `release\CalendarFIF-win32-x64\CalendarFIF.exe`로 다시 걸었고, `npm run desktop:clean`이 `release\0.6.0`을 지웠다. 이제 `release`에는 `CalendarFIF-win32-x64` 하나만 있다. 앞으로도 앱이 켜져 있으면 세션이 닫고 바꿔 넣고 다시 켠다(CLAUDE.md "사용자가 정한 것").
- 정한 것: 버전 번호(`package.json`의 `version`)는 그대로 올린다. 위젯 메뉴와 웹앱이 그 번호로 바뀌었는지 알려 주기 때문이다. 사용자가 없애라고 한 것은 폴더 이름의 번호로 읽었다. → 틀렸으면 번호를 올리지 않게 바꾸면 된다(앱 동작과 무관).

## 정한 것

설계 11절의 1~10에 더해 진행하면서 정한 것:

11. 달력 쪽 높이와 줄 간격 설정이 바로 반영되도록 `main.ts`도 고쳤다. → 비용 없음.
12. 알림·카운트다운 단추는 편집 화면에 알림 자료가 주어질 때만 보인다. → 다른 곳에서 단추만 쓰려면 다시 더해야 한다.
13. 매년 2월 29일 카운트다운은 다음 윤년까지(9년 안) 찾는다. → 비용 없음.
14. 알림 시트를 닫은 뒤 폰에서는 메모 칸이 아니라 편집 화면에 초점을 둔다(글자판이 올라오지 않게). → 폰에서 다시 쓰려면 메모 칸을 한 번 누른다.
15. 이미 울린 알림을 같은 날 더 늦은 시각으로 바꾸면 다시 울린다. 10분 안의 이른 시각으로 되돌려도 다시 울린다. → 드물게 한 번 더 울린다.
16. 위젯은 앱으로 열 때 로그인 토큰을 두 번 새로 받는다(한 번 더 요청). → 비용 거의 없음.
17. 알림 상자를 누를 때 편집 화면이 열려 있으면 고친 것을 저장하고 넘어가고, 알림·카운트다운 시트가 열려 있으면 넘어가지 않고 그 줄만 지운다. → 시트가 열린 동안에는 상자로 날짜를 열 수 없다.
18. 알림 쓰기는 트랜잭션으로 서버의 `editedAt`과 비교하고, 서버에서 지운 항목은 오래된 저장보다 우선한다. → 오프라인에서 고친 항목을 다른 기기에서 지웠으면 고친 것은 버려진다. 기기 시계가 크게 틀리면 그 차이 안의 편집이 버려질 수 있다.
19. `지금 예약`은 저장을 서버가 받은 것을 확인한 뒤 `Scriptable 열기` 링크로 바뀌고 한 번 더 누른다. → 한 번 더 누른다. 연결이 없으면 "연결된 뒤에 다시 누르세요".
20. 오늘의 새 알림 기본 시각은 지금+15분을 15분 단위로 내린 것(23:59까지), 그것이 지났으면 09:00. 다른 날은 09:00.
21. 삭제는 대화 상자 대신 두 번 누르기로 확인한다.
22. 문서만 고친 작업(README)의 검토는 가지 전체 검토에 맡겼다.

사용자: "위젯눌르면 , Scriptable 잠깐 나온 후 사파리에서 열리잖아. 이거 너무 마음에 안드는데 방법이 없는거야?" (2026-11-15 저녁에도 같은 말을 했고 그때는 iOS의 한계라고 안내만 했다.)

사용자에게 한 답: Scriptable이 뜨는 것은 없앨 수 없다(위젯을 누르면 iOS가 그 위젯의 앱을 연다). 홈 화면 앱을 바로 여는 것도 안 된다(iOS에는 다른 앱에서 홈 화면 웹앱을 여는 방법이 없다). Safari로 넘어가는 것은 없앨 수 있다. Scriptable 자체를 없애려면 App Store용 앱과 그 위젯을 만들어야 하고, 유료 개발자 계정과 Mac이 필요해 무료 조건에 맞지 않는다.

한 것:

- 위젯의 Parameter에 `inapp`(또는 `앱안`)을 적으면, 위젯을 눌렀을 때 Safari 대신 Scriptable 안의 웹 화면(WebView)에 달력이 뜬다. 위젯의 누르는 주소가 `scriptable:///run/<스크립트 이름>?open=calendar`가 되고, 그렇게 열린 스크립트는 메뉴 대신 웹앱을 전체 화면으로 띄운다(`src/widget/main.ts`의 `tapUrl`, `openCalendarInApp`).
- 불러오기를 기다리지 않고 바로 띄운다. WebView가 없거나 띄우지 못하면 전처럼 메뉴가 뜬다. 오류 위젯은 늘 웹앱의 주소다.
- 그렇게 열린 실행은 업데이트 확인을 달력을 닫은 뒤에 한다(`update.ts`). 이것은 붙여 넣은 스크립트 쪽의 동작이라, 0.9.0을 붙여 넣은 폰에서는 열기 전에 확인한다(보통 1초 안, 연결이 나쁘면 5초까지).
- 기본(Parameter에 `inapp`이 없을 때)은 바뀌지 않았다.

확인한 것:

- Scriptable 문서: `Script.name()`, `scriptable:///run/이름`(덧붙인 주소 매개변수는 `args.queryParameters`로 온다), `new WebView()`, `loadURL`, `present(fullscreen)`.
- 단위 테스트 1,286개와 `npx tsc --noEmit`이 통과했다. 따로 맡긴 검토에서 Critical은 없었고 Important 둘(불러오기에 시간 제한이 없다, 앱 안의 실행은 열기 전에 업데이트를 확인한다)을 고쳤다.
- 배포 뒤 실제 주소의 버전 파일과 위젯 코드가 0.9.1이고 온전한 것을 확인했다.
- **아이폰에서는 확인하지 못했다.** Scriptable 안의 화면이 어떻게 보이는지, 그 안의 로그인이 다음에도 남는지, 닫지 않고 홈으로 나갔다가 다시 누르면 어떻게 되는지는 모른다.

정한 것(틀렸을 때의 비용):

1. 기본으로 켜지 않고 Parameter로 고르게 했다. → 사용자가 위젯 편집에서 `inapp`을 적어야 한다. 써 보고 좋다고 하면 기본으로 바꾼다.
2. Scriptable 안의 화면은 Safari나 홈 화면 앱과 저장소가 따로다. → 한 번 로그인해야 하고, 서비스 워커가 없어 오프라인에서는 열리지 않으며 열 때마다 내려받는다(홈 화면 앱보다 느릴 수 있다). 푸시 알림 받기는 거기서 켤 수 없다.
3. 달력을 닫으면 Scriptable의 화면이 남는다. → Scriptable에는 홈으로 나가는 기능이 없다.
4. PC 앱은 다시 꾸리지 않았다(위젯만 바뀌었다). → PC 앱의 버전 표시는 0.9.0이고 웹앱은 0.9.1이다.

### 위젯 코드가 Scriptable에 없는 기능(URL)을 쓰던 것 (2026-11-17 아침, 0.9.9, 09:47 배포)

- 0.9.4의 "위젯에서 연 화면" 안내가 나오지 않았다(웹앱이 위젯에서 연 화면인 줄 몰랐다).
- 0.9.6의 "올리지 못한 편집을 위젯에 넘기기"가 돌지 않았다(웹앱이 `window.__calfifPending`을 적지 않았다).

고친 것:

  - 판정(`verdictOf`): 두 번 잇달아 안 그려지면 안 된다(여러 번 쓰는 방법은 그려진 적 없이 한 번 안 그려져도 안 되는 것으로 본다). 그려졌다 안 그려졌다를 두 번 되풀이한 것도 안 되는 것으로 본다(메뉴를 열 때마다 다시 시험하지 않게). 안 되는 것으로 가려진 지 사흘이 지나면 한 번 더 해 본다. 메뉴에서 시험한 뒤 스크립트가 멈췄거나 하자마자 메뉴가 닫히기를 두 번 잇달아 하면 쓰지 않는다. 하고 5초 안에 메뉴나 달력을 닫은 것은 무효다(닫으면 스크립트가 끝나고 그것이 위젯을 그리게 한다). 하고 5초 안에 홈 화면으로 나간 것은 그려졌으면 그려진 것으로, 아니면 판정에 넣지 않는다. 다만 그런 일이 세 번 잇달으면 되던 방법도 모르는 것으로 돌려 다시 시험한다.
  - 기록은 스물여덟 개까지 두고, 방법마다 판정에 들어가는 마지막 여섯 개는 다른 기록에 밀려 나가지 않게 한다(밀려 나가면 같은 시험을 되풀이한다).
- 저장인지는 웹앱이 적어 두는 글로 가린다(`src/widget/pending.ts`의 `savedBetween`): 올리지 못한 편집의 목록에 새 편집이 생기면 저장이다. 편집이 서버에 올라가 목록에서 빠지기만 한 것은 저장이 아니다(앞서 남아 있던 편집이 달력을 열자마자 올라가는 일이 있다). 웹앱은 그 글에 `n`을 넣는다(`pendingTeller`: 목록이 달라질 때마다 하나씩 는다). 스크립트가 읽는 0.3초 사이에 저장하고 올라가 버려도 `n`이 둘 늘어서 저장이 있었음을 안다.
- 닫지 않고 홈 화면으로 나가도 스크립트를 끝내지 않는다(0.9.12를 되돌렸다. 앱 전환으로 돌아와 고쳐도 지켜본다). 위젯을 다시 눌러 새 달력이 뜨면 앞의 실행은 가려진 달력을 더 지켜보지 않는다(보관 파일의 `session`). 그 스크립트는 가려진 달력이 닫힐 때 끝난다(새 달력이 떠 있는 동안 끝내면 무슨 일이 나는지 몰라 끝내지 않는다).
- 위젯에서 연 화면에서는 Firebase SDK의 경고와 오류의 마지막 다섯 줄을 `window.__calfifLog`에 적어 두고(`firebase/app`의 `onLog`), SDK가 콘솔에 적는 그 줄은 막는다(`src/web/widgetLog.ts`). 스크립트가 읽어 메뉴의 상태에 "웹 화면 기록"으로 보인다. SDK의 기록 수준을 끄는 것으로는 안 된다: Firestore는 수준을 보고 기록 자체를 건너뛰어 받는 쪽에도 오지 않는다(검토가 찾았다). "Errors Logged" 상자가 사라지는지는 Scriptable이 콘솔을 언제 가로채는지에 달렸다(우리 것보다 먼저 가로채면 사라지고, 나중이면 남는다). 어느 쪽이든 내용은 메뉴에서 볼 수 있다.
- 메뉴의 상태에 "바로 그리기: setWidget … · ping … · complete … · finish …"(됨, 안 됨, 쓰지 않음, 시험 전)와 마지막 시도 다섯 개를 적는다.
