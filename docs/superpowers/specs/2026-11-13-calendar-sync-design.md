# CalendarFIF 설계: PC ↔ 아이폰 양방향 달력

- 날짜: 2026-11-13
- 상태: 사용자 승인 (2026-11-13)

## 1. 무엇을 왜 만드는가

사용자는 PC 바탕화면 달력(DesktopCal)에 날짜별로 메모를 적는다. PC에서 적은 내용이 휴대폰에도 보이는 점이 이 달력을 쓰는 이유다. 이 쓰임새를 직접 만든 달력으로 옮긴다. 대상 기기는 Windows PC 한 대와 아이폰 17 Pro 한 대다.

사용자가 말한 요구:

1. PC와 아이폰만 연동한다.
2. 지금 있는 데이터를 그대로 다 옮긴다.
3. 날짜별로 입력한 내용과 날짜 칸 배경색이 동기화된다.
4. 양방향이다. PC에서 고치면 아이폰에, 아이폰에서 고치면 PC에 반영된다.
5. 아이폰에서는 위젯으로 본다.
6. 무조건 무료다.
7. 기능은 다 쓰고 싶다.
8. DesktopCal을 분석해서 만든다.
9. CalendarFIF가 충분히 쓸 만해질 때까지 DesktopCal을 계속 쓰고, 그때 전환한다.
10. 듀얼 모니터를 쓴다. CalendarFIF는 DesktopCal이 떠 있는 화면의 반대쪽 화면에 띄운다.

7번은 한 번에 하지 않고 단계로 나눈다(작성자 결정). 이 문서의 범위는 2~6번과 9~10번이 되는 첫 버전이다. 나머지 기능은 부록 B에 단계별로 적는다.

## 2. 목표, 범위 밖, 실패 조건

### 목표 (첫 버전)

- **G1.** PC와 아이폰에서 날짜별 메모와 배경색을 보고 고친다. 줄마다 완료 표시(취소선)를 켜고 끈다.
- **G2.** 양쪽이 온라인일 때 한쪽에서 저장하면, 다른 쪽에 열려 있는 화면이 5초 안에 바뀐다. (5초는 작성자가 제안한 목표치)
- **G3.** 기존 기록을 빠짐없이 옮긴다. 2026-11-13 기준 날짜 칸 845행 중 내용이나 배경색이 있는 789행이다.
- **G4.** 아이폰 홈 화면 위젯에서 이번 달의 메모와 배경색을 본다.
- **G5.** PC에서는 바탕화면에 붙어 있는 달력으로 쓴다. 듀얼 모니터에서 띄울 화면을 고른다. 배경은 투명해서 바탕화면 그림이 비쳐 보인다(사용자가 2026-11-13에 추가).
- **G6.** 비용은 0원이다.
- **G7.** 전환 전까지는 DesktopCal에 적은 내용이 CalendarFIF와 아이폰에 자동으로 따라온다. (작성자 제안)

### 범위 밖 (첫 버전에서는 하지 않는다)

- 알림과 반복 일정. 기존 29건은 옮기지 않고 DesktopCal 데이터 파일에 그대로 둔다.
- 음력, 공휴일, 절기 표시.
- 스티커 메모, 시간표, 구글·아웃룩·iCloud 캘린더 연동, AI 연동.
- 여러 사람이 함께 쓰는 달력, 안드로이드.
- 메모 수정 이력. DesktopCal에 이력이 남은 23행의 과거 내용은 옮기지 않는다.

### 실패 조건

- 기록이 조용히 사라지거나 덮어써진다.
- 돈이 든다.
- 본인 계정이 아닌 곳에서 기록을 읽을 수 있다.
- DesktopCal의 서버에 접속하거나, 그 프로그램의 코드나 이미지를 가져다 쓴다. 읽는 것은 사용자 PC에 있는 본인 데이터 파일뿐이다.

| 동기화 코어 | 웹앱과 PC 앱 안 | 기기 안 저장, 대기 중인 편집 관리, 병합, Firestore 읽기와 쓰기 |
| 웹앱 | 아이폰 Safari, PC 브라우저 | 달력 보기와 편집 |
| 위젯 스크립트 | 아이폰 Scriptable | 이번 달을 읽어 위젯으로 그리기. 읽기만 한다. |
| PC 앱 | Windows | 웹앱 화면을 바탕화면 창에 띄우기 |
| 가져오기 도구 | 개발 PC 명령줄 | DesktopCal 기록을 Firestore로 옮기기 |

웹앱과 PC 앱은 같은 화면 코드와 같은 동기화 코어를 쓴다. 동기화 로직은 한 벌만 있다.

흐름:

1. PC나 아이폰에서 날짜를 고치고 저장한다.
2. 동기화 코어가 편집을 기기 안 대기열에 넣고, 온라인이면 Firestore에 올린다.
3. Firestore가 그 달 문서를 구독 중인 다른 기기에 바뀐 내용을 보낸다.
4. 다른 기기의 화면이 바뀐다.
5. 위젯은 iOS가 갱신할 때 Firestore에서 그 달 문서를 읽어 다시 그린다.

## 6. 데이터 모델

### 문서

경로: `users/{uid}/months/{YYYY-MM}`. 한 달이 문서 하나다.

```json
{
  "days": {
    "13": {
      "text": "10:00 회의\n택배 받기",
      "color": "F12424",
      "editedAt": 1794533568000,
      "editedBy": "pc"
    }
  },
  "updatedAt": "<서버 시각>"
}
```

- `days`의 키는 두 자리 날짜다("01"~"31").
- `text`: 줄바꿈은 `\n`이다. 줄 끝 공백과 앞뒤 빈 줄은 저장하지 않는다. 줄이 `[+]`로 시작하면 완료한 줄이다. DesktopCal과 같은 표기라서 변환 없이 옮긴다.
- `color`: 빈 문자열(배경 없음) 또는 `#` 없는 대문자 RGB 16진수 6자리다.
- `editedAt`: 고친 기기의 시계로 잰 시각(epoch 밀리초)이다.
- `editedBy`: 어느 기기에서 고쳤는지 적는 짧은 이름이다. 문제를 추적할 때만 쓰고 병합에는 쓰지 않는다.
- 내용도 배경색도 없는 날짜는 키를 지운다.

한 달을 문서 하나에 넣는 이유는 읽기 횟수다. 위젯과 달 보기가 문서 1개만 읽는다. 날짜마다 문서를 두면 위젯이 갱신될 때마다 30~42개를 읽는다. 문서 크기 한도는 1MiB이고, 기존 기록에서 가장 긴 하루가 446자라서 여유가 크다.

### 계정과 보안 규칙

- Firebase 인증의 이메일/비밀번호 방식을 쓴다. 사용자는 1명이고 콘솔에서 직접 만든다. 가입 화면은 만들지 않는다.
- 구글 로그인 대신 이 방식을 쓰는 이유는 위젯 스크립트가 주소 호출만으로 로그인해야 하기 때문이다.
- Firestore 규칙: `users/{uid}` 아래는 그 사용자 본인의 uid로 로그인했을 때만 읽고 쓴다. 허용하는 uid를 규칙에 한 개로 못 박는다. 그 밖의 경로는 전부 거부한다.

## 7. 동기화 규칙

저장한 편집은 기기 안 대기열에 먼저 들어간다. 온라인일 때 서버의 최신 내용과 합쳐서 올린다.

1. 화면에 보이는 내용은 "서버에서 받은 달 문서 + 아직 못 올린 대기 편집"이다.
2. 편집을 저장하면 대기열에 `{ monthId, day, base, next, editedAt }`를 넣는다. `base`는 편집 화면을 열 때 보이던 `{text, color}`이고 `next`는 저장한 `{text, color}`다. 같은 날짜의 대기 편집이 이미 있고, 아직 올리기 시작하지 않았고, 새 편집이 그 대기 편집의 결과 위에서 고친 것(새 편집의 `base`가 그 편집의 `next`와 같음)이면 `base`는 두고 `next`와 `editedAt`만 바꾼다. 그렇지 않으면 새 편집을 따로 뒤에 넣고, 올릴 때 순서대로 이어서 적용한다. 다른 탭에서 연 편집이나 서버 내용이 바뀐 뒤의 편집을 옛 `base`로 합치면 줄이 사라지기 때문이다(2026-11-13 최종 검토에서 고침). 그 편집은 서버에 들어갔을 수 있어서 옛 `base`로 합치면 되돌린 내용이 사라지기 때문이다. (2026-11-13 구현 검토에서 추가)
3. 올릴 때는 트랜잭션으로 서버의 그 날짜 값 `S`를 읽는다.
   - `S`가 `next`와 같으면 쓰지 않는다.
   - `S`가 `base`와 같으면 `next`를 쓴다.
   - 그 밖에는 아래 병합 규칙으로 합친 값을 쓴다.
   - 성공하면 대기열에서 지운다. 실패하면 두었다가 다음 기회에 다시 올린다.
4. 올리는 시점: 저장 직후, 앱을 열 때, 온라인으로 돌아올 때, 화면이 다시 보일 때.
5. 받기: 보고 있는 달과 앞뒤 달 문서를 실시간으로 구독한다.

### 병합 규칙

같은 날짜를 양쪽에서 고쳤을 때 적용한다.

- **메모는 줄 단위로 합친다.** 서버 본문 `S.text`에서 시작한다.
  - 내가 지운 줄(`base`에 있고 `next`에 없는 줄)은 `S`에서 한 번 지운다.
  - 내가 추가한 줄(`next`에 있고 `base`에 없는 줄)은 넣는다. `next`에서 그 줄 바로 앞에 있던 줄이 `S`에 있으면 그 뒤에, 없으면 맨 끝에 넣는다.
  - 서버 쪽에서도 똑같은 줄을 추가했으면 한 번만 남긴다.
  - 같은 글의 줄이 여러 개면 개수로 센다. 줄을 고친 것은 "지움 + 추가"로 본다.
  - 완료 표시를 켜고 끄는 것도 줄을 고친 것으로 본다. 한쪽에서 완료로 바꾸는 동안 다른 쪽이 그 줄의 글을 고쳤으면 두 줄이 다 남는다.
- **배경색은 바꾼 쪽의 색이 남는다.**
  - 나만 바꿨으면(`next.color ≠ base.color`이고 `S.color = base.color`) 내 색이다.
  - 서버 쪽만 바꿨으면(`next.color = base.color`) 서버 색이다.
  - 양쪽이 다 바꿨으면 나중에 고친 쪽이 남는다. 내 `editedAt`이 `S.editedAt`보다 늦으면 내 색, 아니면 서버 색이다.
- 합친 결과의 `editedAt`은 둘 중 큰 값이다.

예: 원래 `A, B` 두 줄이었다. 아이폰이 오프라인에서 `C`를 추가했고(`A, B, C`), 그 사이 PC가 `B`를 `B2`로 고쳤다(`A, B2`). 아이폰이 다시 연결되면 결과는 `A, B2, C`다.

결과적으로:

- 서로 다른 날짜를 고치면 둘 다 남는다.
- 같은 날짜에 양쪽에서 줄을 추가하면 둘 다 남는다.
- 한쪽에서 지운 줄은 지워진다.
- 같은 줄을 양쪽에서 다르게 고치면 두 줄이 다 남는다. 사용자가 보고 정리한다.
- 한쪽은 배경색만, 다른 쪽은 메모만 고치면 둘 다 남는다.

기기 시계는 양쪽이 배경색을 다 바꿨을 때의 판정에만 쓴다. 메모 병합은 시계에 기대지 않는다.

## 8. 구성 요소별 설계

### 8.1 웹앱

화면 시안: https://claude.ai/artifact/KWwUzo4fMcTHi8saqHyHDa (예시 데이터, 좁은 화면 기준)

- 화면은 넷이다: 로그인, 달력(월), 날짜 편집, 설정(로그아웃, 위젯 설치 안내).
- 달력: 이전 달, 다음 달, 오늘로 이동, 좌우로 밀어 넘기기. 칸에는 날짜, 배경색, 메모 줄을 칸에 들어가는 만큼 보여 주고 넘치면 `+n`으로 표시한다. 일요일은 빨강, 토요일은 파랑이다.
- 날짜 편집: 여러 줄 메모, 줄마다 완료 표시 켜고 끄기, 배경색 고르기, 취소와 저장.
- 완료한 줄은 달력 칸에서 `[+]` 없이 취소선으로 보인다.
- 배경색 팔레트는 DesktopCal과 같은 22색이다(부록 A). 팔레트에 없는 기존 색도 그대로 보인다.
- 배경색 표시: 저장된 색을 옅게 깔아 글자가 읽히게 한다. 저장 값은 바꾸지 않는다.
- 상태 표시: 동기화됨, 올리는 중, 오프라인(대기 n건).
- 좁은 화면(아이폰)과 넓은 화면(PC) 배치를 둘 다 갖는다.
- 오프라인: 전에 본 달은 볼 수 있다. 편집은 대기열에 들어간다.
- 주소: `https://<프로젝트 ID>.web.app`. 주소 뒤에 `#2026-11-13`을 붙이면 그 날짜의 편집 화면이 바로 열린다. 위젯이 이 주소를 쓴다.
- 밝은 화면과 어두운 화면을 둘 다 지원한다.

### 8.2 위젯 (Scriptable)

- 자바스크립트 파일 하나다. 설정 화면에서 복사해 Scriptable에 붙여 넣는다. 파일에는 프로젝트 주소 같은 공개 설정만 들어가고 비밀번호는 들어가지 않는다.
- 처음 한 번 Scriptable 안에서 실행하면 이메일과 비밀번호를 묻는다. 로그인에 성공하면 갱신 토큰만 아이폰 키체인에 저장한다. 비밀번호는 저장하지 않는다.
- 갱신할 때마다 토큰으로 로그인하고 이번 달 문서 1개를 읽는다.
- 큰 위젯(필수): 월 이름, 요일 줄, 주 단위 줄. 칸마다 날짜, 옅게 깐 배경색, 메모 2~3줄. 오늘을 강조한다. 완료한 줄은 취소선으로 그린다.
- 다른 크기의 위젯은 빌더가 판단한다.
- 위젯을 누르면 웹앱이 열린다.
- 읽기에 실패하면 마지막으로 받은 내용을 "오프라인" 표시와 함께 보여 준다. 로그인 전이면 로그인 방법을 안내하는 문구를 보여 준다.
- 다음 갱신 희망 시각을 15분 뒤로 알린다. 실제 시점은 iOS가 정한다.

### 8.3 PC 앱

- Electron으로 만든다(작성자 결정). 이 PC에 Node가 있어 추가 설치 없이 만들 수 있다. 화면은 웹앱 코드를 앱 안에 넣어 쓰고, 호스팅 주소에 기대지 않는다.
- 창: 테두리가 없고 작업 표시줄에 나타나지 않는다. 바탕화면 층에 머물러 다른 창 뒤에 있다. 위치와 크기를 바꿀 수 있고 기억한다.
- 배경은 투명하다. 바탕화면 그림이 달력 뒤로 비쳐 보인다(사용자 요청, 2026-11-13). 투명한 정도와 날짜 칸의 모양은 ③을 시작할 때 시안으로 정한다. DesktopCal이 창을 바탕화면에 붙이고 투명하게 그리는 방식은 ③의 첫 작업에서 분석한다. 실행 파일 분석에는 REA를 쓰는데, 이 PC에는 정밀 분석 엔진(Ghidra 또는 IDA)이 설정되어 있지 않아 PE 검사까지만 된다. 정밀 분석이 필요하면 그때 사용자와 정한다.
- 트레이 아이콘: 보이기/숨기기, 위치 잠금, 시작할 때 실행, 종료.
- Windows 시작 시 자동 실행. 중복 실행 방지.
- 듀얼 모니터: 띄울 모니터를 고를 수 있고 기억한다. 그 모니터가 연결되어 있지 않으면 주 모니터에 띄운다.
- DesktopCal과 동시에 떠 있어도 서로 방해하지 않는다. 사용자는 전환 전까지 DesktopCal을 한쪽 모니터에, CalendarFIF를 반대쪽 모니터에 둔다.
- 창을 바탕화면 층에 두는 방법은 이 단계의 첫 작업으로 이 PC에서 실험해 정한다. 안 되면 "항상 맨 뒤에 있는 일반 창"으로 물러난다.
- DesktopCal은 건드리지 않는다. 지울지는 사용자가 정한다.

### 8.4 가져오기 도구

- 명령줄 도구다. 두 가지로 돈다.
  - **한 번 가져오기**: 지금 있는 기록을 올리고 끝난다.
  - **따라가기**: 켜 두면 DesktopCal의 데이터 파일이 바뀔 때마다 바뀐 날짜만 다시 올린다. 전환 기간에 쓴다.
- DesktopCal의 `calendar.db` 원본에는 쓰지 않고 잠그지도 않는다. 파일을 복사해 복사본만 읽는다. 복사할 때 DesktopCal이 쓰는 중이면(저널 파일이 있으면) 잠시 뒤 다시 복사한다. 복사본은 무결성 검사를 통과해야 쓴다.
- 변환 규칙은 부록 A에 있다.
- 미리보기 모드: 올리지 않고 건수, 연도별 분포, 색 변환표를 보여 준다. 사용자가 날짜 두세 개의 색을 눈으로 확인한다.
- 올리기: 사용자 계정으로 로그인해 달 문서로 쓴다. `editedAt`은 DesktopCal의 수정 시각, `editedBy`는 `import`다.
- 날짜별로 "지난번에 가져온 내용"을 이 PC의 상태 파일에 기억한다. 다시 돌 때는 지난번과 달라진 날짜만 올린다. 올리는 방식은 7절과 같다. 지난번 내용이 `base`, 지금 내용이 `next`다. 그래서 그 사이 아이폰에서 추가한 줄이 지워지지 않는다.
- 상태 파일이 아예 없는데 클라우드에 그 날짜가 이미 있고 내용이 다르면, 클라우드 쪽 `editedAt`이 DesktopCal의 수정 시각보다 이를 때만 덮어쓴다. 이렇게 건너뛴 날짜는 상태 파일에 적지 않는다. 다음에 돌 때 합쳐진다.
- 상태 파일은 있는데 그 날짜만 없으면(휴대폰에서만 적은 날짜) 빈 값을 `base`로 보고 7절 방식으로 합친다. 휴대폰에서 적은 내용과 DesktopCal에서 적은 내용이 둘 다 남는다(2026-11-13 최종 검토에서 고침).
- DesktopCal에서 사라진 날짜가 많으면 올리지 않고 멈춘다. 파일이 비었거나 다른 파일로 바뀌었을 때 옮긴 기록이 한꺼번에 지워지는 것을 막는다. 정말 지우려면 `--allow-deletes`를 붙여 한 번 가져오기를 실행한다.
- 끝나면 다시 읽어 건수를 원본과 맞춰 보고 보고서를 출력한다.
- 사용자의 `calendar.db`, 상태 파일, 내보낸 기록, 로그인 정보는 저장소에 넣지 않는다.

### 전환 기간

사용자는 CalendarFIF가 충분히 쓸 만하다고 판단할 때까지 DesktopCal을 계속 쓴다.

- 전환 전까지 원본은 DesktopCal이다. 사용자는 PC에서 DesktopCal에 계속 적는다.
- CalendarFIF는 반대쪽 모니터에 띄워 둔다. ③ 전에는 브라우저 창으로, ③ 뒤에는 바탕화면 앱으로 띄운다.
- 따라가기가 DesktopCal에 새로 적은 내용을 자동으로 올린다. 그래서 CalendarFIF 화면과 아이폰 위젯이 DesktopCal과 같은 내용을 보여 준다.
- 방향은 DesktopCal → CalendarFIF 한쪽뿐이다. 아이폰이나 CalendarFIF에서 고친 내용은 CalendarFIF와 아이폰에는 남지만 DesktopCal에는 나타나지 않는다.
- 전환하는 날: 따라가기로 마지막 내용까지 올라간 것을 확인한다. 사용자가 DesktopCal을 끄고 자동 실행을 해제한다. 따라가기를 끈다. 이후 원본은 CalendarFIF다.

## 10. 사용자가 직접 할 일

1. 개인 Google 계정으로 Firebase 프로젝트를 만든다. 무료이고 카드를 등록하지 않는다. 화면별 안내는 `docs/firebase-setup.md`에 있다.
   - 프로젝트 생성, Firestore 데이터베이스 생성(서울 리전), 인증에서 이메일/비밀번호 켜기와 사용자 1명 추가, 웹 앱 등록.
2. 이 PC에서 Firebase 명령줄 도구에 로그인한다. 브라우저 창이 뜨는 로그인이라 직접 해야 한다.
3. 아이폰에 Scriptable을 설치하고, 위젯 스크립트를 붙여 넣고, 홈 화면에 위젯을 추가한다.
4. 아이폰에서 눌러 보고 결과를 알려 준다.

## 부록 A. DesktopCal 데이터 형식

분석 방법: 데이터 파일(SQLite)의 스키마와 집계를 조회했고, 실행 파일에서 문자열을 추출했다. REA의 심층 분석기는 Ghidra가 설정되어 있지 않아 쓰지 못했다. 이번 범위에는 필요하지 않았다.

- 파일: `%APPDATA%\CalendarTask\Db\calendar.db` (DesktopCal 3.32.310.9371)
- 날짜 칸은 `item_table`에 있다. 2026-11-13 기준 845행이다.

| 열 | 뜻 | 변환 |
|---|---|---|
| `it_unique_id` | `dkcal_mdays_YYYYMMDD` | 날짜로 바꾼다. 모든 행이 이 형식이다. |
| `it_content` | 메모 본문 | 줄바꿈 `\r\n`을 `\n`으로 바꾼다. `&lt;` `&gt;` `&quot;` 세 가지만 원래 글자로 되돌린다. `&`는 그대로 저장되어 있으므로 다른 변환은 하지 않는다. |
| `it_bgcolor` | 배경색 | 아래 색 변환 참고. |
| `it_stime` | 마지막 수정 시각(초) | 1000을 곱해 `editedAt`으로 쓴다. 모든 행에 값이 있다. |
| `it_history` | 과거 내용 | 옮기지 않는다. |

- 내용도 배경색도 없는 56행은 건너뛴다. 옮길 행은 789행이다(메모가 있는 752행, 배경색만 있는 37행).
- 연도별 행 수: 2023년 108, 2024년 269, 2025년 245, 2026년 213, 2027년 7, 2028년 1, 2029년 1, 2047년 1.
- 가장 긴 하루는 446자, 18줄이다.

### 색 변환

저장 값은 앞의 0이 빠진 BGR 16진수다. 6자리가 되도록 앞을 0으로 채운 뒤 바이트 순서를 뒤집어 RGB로 만든다. 근거는 세 가지다.

- DesktopCal의 팔레트 정의(`context_menu.lua`)에 같은 값이 들어 있다. 예: `0x2424F1`.
- 그 팔레트를 BGR로 읽어야 첫 줄이 분홍, 주황, 노랑, 연두, 파랑, 보라 순서가 된다.
- 사용자는 빨강 배경을 쓴다고 했고, 이 해석에서 가장 많이 쓰인 두 값이 빨강이 된다.

DesktopCal의 배경색 팔레트 22색(RGB로 바꾼 값, 화면에 놓인 순서):

### `[+]` 표시

메모 줄 1,452개 중 116개가 `[+]`로 시작한다. 완료한 줄이라는 뜻이고 DesktopCal은 이 줄을 취소선으로 그린다. 근거: DesktopCal의 화면 스크립트(`history_search.lua`)에 `[+]`로 취소선을 그린다는 주석과 판정식 `^%s*%[%+%]`가 있다. 기존 기록에서는 116줄 모두 줄 맨 앞에 공백 없이 붙어 있다(`[+]내용`).

### 글자색

DesktopCal은 글자색을 `<font>` 태그로 저장한다. 기존 기록에는 이 태그가 하나도 없다. 본문에 있는 `&lt;` `&gt;` `&quot;`는 사용자가 직접 친 `<` `>` `"` 글자다. 따라가기 중에 `<font>` 태그가 든 줄이 나오면 태그만 떼고 글자는 남기며, 보고서에 건수를 적는다.
