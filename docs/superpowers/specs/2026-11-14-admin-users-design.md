# 관리자와 사용자 추가 설계

작성: 2026-11-14. 사용자가 방향을 정했고(아래 1절), 나머지는 작성자가 정했다(8절). 사용자는 남은 작업을 묻지 말고 진행하라고 했다.

## 1. 사용자가 정한 것

- 관리자를 둔다. 관리자는 지금 CalendarFIF에 로그인해서 쓰는 계정이다(기록 789일이 들어 있는 계정).
- 관리자로 로그인하면 사용자를 추가할 수 있다.
- 추가한 사용자는 각자 자기 달력을 쓴다. 서로의 메모를 볼 수 없고, 관리자도 남의 메모를 보지 못한다.
- 무료 범위(Firebase Spark) 안에서 한다.

## 2. 목표와 하지 않는 것

목표

- U1. 관리자가 웹앱(또는 PC 앱)의 설정에서 이메일과 처음 비밀번호를 넣어 사용자를 추가한다.
- U2. 추가된 사용자는 그 이메일과 비밀번호로 로그인해서 자기 달력을 쓴다. 동기화, 아이폰 홈 화면 앱, PC 앱이 관리자와 똑같이 동작한다.
- U3. 관리자가 사용자의 사용을 중지하거나 다시 허용하고, 목록에서 지울 수 있다.
- U4. 허가받지 않은 계정은 어떤 달력 문서도 읽거나 쓰지 못한다. 화면이 아니라 보안 규칙이 막는다.
- U5. 누구나 자기 비밀번호를 바꿀 수 있고, 잊었을 때는 메일로 다시 정할 수 있다.
- U6. 관리자의 기존 기록, 가져오기(`npm run import`), 따라가기는 그대로 동작한다.

하지 않는 것

- 달력 공유(여러 사람이 달력 하나를 같이 보거나 고치는 것).
- 관리자가 다른 사용자의 메모를 보거나 고치거나 지우는 것.
- 관리자를 여러 명 두는 것, 화면에서 관리자를 바꾸는 것.
- 사용자의 로그인 계정 자체를 앱에서 지우는 것(무료 범위에서는 서버 없이 할 수 없다. Firebase 콘솔에서 한다).
- 가입 신청 화면(스스로 가입하는 것).

실패로 보는 것

- 허가받지 않은 계정이 문서를 하나라도 읽을 수 있다.
- 사용자를 추가하다가 관리자가 로그아웃되거나 다른 계정으로 바뀐다.
- 저장소(공개)에 관리자의 이메일이나 계정 ID가 들어간다.
- 관리자 본인의 달력이 느려지거나 읽기 비용이 늘어난다.

## 3. 방식

### 3.1 살펴본 방법

| 방법 | 내용 | 판단 |
|---|---|---|
| A. 허가 목록 문서 + 화면에서 계정 만들기 | Firestore에 `access/{uid}` 문서를 두고 보안 규칙이 그 문서를 확인한다. 관리자의 화면이 두 번째 Firebase 앱 인스턴스로 계정을 만든다. | 채택. 서버가 없어도 되고 무료다. |
| B. Cloud Functions + Admin SDK(커스텀 클레임) | 서버 함수가 계정을 만들고 권한을 토큰에 넣는다. | 버림. Functions는 결제 수단 등록(Blaze)이 필요하다. |
| C. 관리자가 Firebase 콘솔에서 계정을 만들고 규칙에 ID를 추가 | 화면 없이 콘솔과 배포로 한다. | 버림. "로그인했을 때 사용자 추가"가 아니고, 추가할 때마다 배포가 필요하다. |
| D. 스스로 가입 + 관리자 승인 | 가입 화면을 열어 두고 관리자가 승인한다. | 버림. 사용자가 원한 것은 관리자가 추가하는 것이고, 가입 화면은 모르는 사람의 신청을 받게 된다. |

### 3.2 데이터

`access/{uid}` 문서 (관리자와 각 사용자에 하나씩)

| 필드 | 값 |
|---|---|
| `email` | 문자열. 관리자의 목록에 보이는 이름이다. |
| `role` | `'admin'` 또는 `'user'`. 화면이 쓰는 표시다. 권한은 규칙이 정한다. |
| `disabled` | 불리언. 참이면 사용 중지다. |
| `createdAt` | 숫자(ms). |

달력 문서는 지금과 같다: `users/{uid}/months/{YYYY-MM}`. 경로가 이미 사용자별이라 옮길 것이 없다.

### 3.3 보안 규칙

관리자는 배포할 때 규칙에 들어가는 계정 ID(`.env.local`의 `OWNER_UID`, 지금 쓰는 값 그대로)다. 저장소에는 자리 표시(`__OWNER_UID__`)만 있다.

```
function isAdmin() { return request.auth != null && request.auth.uid == '__OWNER_UID__'; }
function isActive(uid) {
  return exists(/databases/$(database)/documents/access/$(uid))
    && get(/databases/$(database)/documents/access/$(uid)).data.disabled != true;
}

match /users/{uid}/months/{monthId} {
  allow read, write: if request.auth != null
    && request.auth.uid == uid
    && monthId.matches('^[0-9]{4}-[0-9]{2}$')
    && (uid == '__OWNER_UID__' || isActive(uid));
}

match /access/{uid} {
  allow get: if request.auth != null && (request.auth.uid == uid || isAdmin());
  allow list: if isAdmin();
  allow create, update: if isAdmin() && 문서 모양 검사
    && (request.resource.data.role == 'admin') == (uid == '__OWNER_UID__')
    && (uid != '__OWNER_UID__' || request.resource.data.disabled == false);
  allow delete: if isAdmin() && uid != '__OWNER_UID__';
}
```

- 관리자 본인의 달력은 `uid == '__OWNER_UID__'`에서 바로 통과해서 `access` 문서를 읽지 않는다. 읽기 비용이 늘지 않고, 가져오기도 지금 그대로 동작한다.
- 일반 사용자는 요청마다 `access` 문서 한 번을 더 읽는다(무료 한도 하루 5만 건에 비해 작다).
- 사용자는 자기 `access` 문서를 읽을 수만 있다. 스스로 중지를 풀거나 관리자가 될 수 없다.
- 관리자도 다른 사용자의 `users/{uid}/months`는 읽지 못한다(`request.auth.uid == uid`).

### 3.4 계정 만들기

Firebase의 화면용 SDK로 계정을 만들면 그 계정으로 로그인이 바뀐다. 그래서 관리자의 화면은 이름이 다른 두 번째 Firebase 앱 인스턴스를 잠깐 만들어(로그인 정보를 저장하지 않는 설정) 거기서 계정을 만들고, 받은 계정 ID로 `access/{uid}` 문서를 쓴 뒤 그 인스턴스를 지운다. 관리자의 로그인은 그대로다.

- 이미 있는 이메일이면: 넣은 비밀번호로 그 인스턴스에서 로그인해 본다. 맞으면 그 계정 ID로 `access` 문서를 쓴다(계정만 만들어지고 허가가 안 붙은 경우와, 목록에서 지운 사용자를 다시 넣는 경우). 틀리면 "이미 있는 이메일입니다. 그 계정의 비밀번호를 넣으면 다시 등록합니다."
- 비밀번호는 8자 이상.
- 이 방식은 프로젝트의 "이메일 가입 허용"이 켜져 있어야 한다(기본값이 켜짐). 모르는 사람이 계정을 만들 수는 있지만 `access` 문서가 없어서 아무것도 읽지 못한다.

### 3.5 화면

- 로그인한 뒤 화면은 `access/{내 uid}`를 지켜본다.
  - 문서가 있고 `role`이 `admin`: 설정에 "사용자 관리"가 보인다.
  - 문서가 있고 중지가 아님: 보통 사용자.
  - 문서가 없음: 문서를 `role: 'admin'`으로 만들어 본다. 규칙상 관리자 계정만 성공한다(관리자의 첫 로그인 때 한 번). 실패하면 "허가받지 않은 계정"이다.
  - 중지됨 또는 허가받지 않음: 달력 대신 안내 화면. "이 계정은 사용 허가를 받지 않았습니다." 또는 "관리자가 이 계정의 사용을 중지했습니다." 와 로그아웃 단추.
- 달력은 이 확인을 기다리지 않고 바로 뜬다(관리자의 화면이 늦어지지 않게). 확인 결과가 막힘이면 그때 안내 화면으로 바꾼다.
- 설정 화면(웹앱과 PC 앱의 계정 쪽)에 추가되는 것
  - 모든 사용자: "비밀번호 변경"(지금 비밀번호, 새 비밀번호).
  - 관리자: "사용자 관리" 단추. 누르면 사용자 관리 화면이 열린다.
- 사용자 관리 화면: 사용자 목록(이메일, 상태), 줄마다 "사용 중지"/"다시 허용", "비밀번호 재설정 메일", "목록에서 지우기"(한 번 더 확인). 아래에 추가 양식(이메일, 처음 비밀번호, "추가").
- 로그인 화면: "비밀번호를 잊었습니다"를 누르면 적어 둔 이메일로 재설정 메일을 보낸다.

### 3.6 PC 앱

PC 앱의 설정 "계정" 쪽이 같은 부품을 쓴다. PC 앱은 Auth를 팝업 처리기 없이 만드는데, 두 번째 인스턴스도 같은 방식으로 만든다. 원격 페이지를 읽지 않는다.

## 4. 오류와 경계

- 계정은 만들어졌는데 `access` 문서 쓰기가 실패: 오류를 보이고, 같은 이메일과 비밀번호로 다시 "추가"하면 3.4의 "이미 있는 이메일" 길로 이어진다.
- 오프라인: 사용자 추가와 목록 변경은 연결이 있어야 한다. 실패를 그대로 알린다. 대기열에 넣지 않는다.
- 사용이 중지된 사용자의 대기 중인 편집: 올리지 못하고 기기에 남는다(지금의 "권한이 없어 올리지 못했습니다"와 같다). 다시 허용되면 올라간다.
- 관리자 자신은 중지하거나 지울 수 없다(규칙과 화면 둘 다).
- 이메일 대소문자와 앞뒤 공백: 소문자로 바꾸고 다듬어서 쓴다.

## 5. 시험

- 규칙 시험(에뮬레이터): 관리자는 `access` 문서 없이 자기 달을 읽고 쓴다. 허가된 사용자는 자기 달만 읽고 쓴다. 허가 없는 계정, 중지된 계정은 못 한다. 관리자는 남의 달을 못 읽는다. `access`는 관리자만 쓰고 목록을 본다. 사용자는 자기 것만 읽는다. 관리자 문서를 `user`로 바꾸거나 중지하거나 지울 수 없다. 사용자를 `admin`으로 만들 수 없다.
- 단위 시험: 접근 상태 계산, 사용자 추가의 갈래(새 계정, 이미 있는 계정과 맞는 비밀번호, 틀린 비밀번호, 문서 쓰기 실패), 화면 부품.
- 에뮬레이터 흐름 시험: 관리자가 사용자를 추가하고도 관리자의 로그인이 유지된다. 추가된 사용자가 로그인해서 쓰고 읽는다. 중지하면 막힌다.

## 6. 배포와 사용자가 할 일

- 배포는 지금처럼 `npm run deploy`(웹앱과 규칙). `.env.local`은 바꾸지 않는다.
- 사용자가 할 일은 없다. 배포 뒤 관리자로 한 번 로그인하면 관리자 표시가 만들어진다.
- 새 사용자에게 알려 줄 것: 주소, 이메일, 처음 비밀번호, 그리고 설정에서 비밀번호를 바꾸라는 말.

## 7. 비용

- Auth: 이메일 로그인은 무료 범위가 넉넉하다(월 5만 명).
- Firestore: 사용자 한 명이 달을 넘길 때마다 읽는 문서가 몇 개 늘 뿐이다. 무료 한도(하루 읽기 5만, 쓰기 2만, 저장 1GiB) 안이다. 사용자가 수십 명이 되면 다시 본다.

## 8. 작성자가 정한 것 (사용자가 바꿀 수 있다)

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 사용자 추가는 관리자가 이메일과 처음 비밀번호를 정하는 방식 | 메일이 스팸으로 빠질 걱정 없이 바로 쓸 수 있다 | 관리자가 처음 비밀번호를 안다. 사용자가 바꾸면 된다 |
| "지우기"는 허가만 지운다. 로그인 계정과 그 사람의 메모는 남는다 | 무료 범위에서는 서버 없이 남의 계정을 지울 수 없다 | 완전히 지우려면 Firebase 콘솔에서 지워야 한다 |
| 관리자는 한 명이고 배포할 때 정해진다 | 규칙이 단순하고 안전하다 | 관리자를 바꾸려면 `.env.local`을 고쳐 다시 배포한다 |
| 비밀번호 재설정은 Firebase가 보내는 메일로 한다 | 무료이고 서버가 필요 없다 | 메일이 영어 양식이거나 스팸함에 들어갈 수 있다 |
| 사용자 관리는 설정에서 여는 별도 화면 | 아이폰 설정 화면이 길어지지 않는다 | 한 번 더 눌러야 한다 |
