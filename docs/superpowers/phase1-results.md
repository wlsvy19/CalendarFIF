# ① 단계 결과 (2026-11-13)

① 단계(동기화 + 웹앱 + DesktopCal 기록 가져오기)가 끝났다. 이 문서는 무엇이 확인됐는지, 진행하면서 사용자 대신 정한 것이 무엇인지, 무엇을 미뤄 두었는지를 적은 것이다. 계획은 `plans/2026-11-13-phase1-sync-web-import.md`, 설계는 `specs/2026-11-13-calendar-sync-design.md`에 있다.

## 확인된 것

| 완료 기준 (설계 9절) | 결과 |
|---|---|
| PC 브라우저와 아이폰 Safari에서 같은 계정으로 로그인한다 | 사용자가 확인했다 |
| 한쪽에서 고친 메모와 배경색이 다른 쪽에 5초 안에 보인다 | 사용자가 PC 두 창, 아이폰↔PC 양쪽 방향으로 확인했다 |
| 가져오기 보고서의 건수가 원본과 맞는다 | 원본 날짜 789 / 클라우드와 같음 789 / 다름 0 / 클라우드에 없음 0 |
| 따라가기를 켜 두면 DesktopCal에 적은 내용이 1분 안에 웹앱에 보인다 | 사용자가 확인했다 |
| 오프라인에서 고친 내용이 연결되면 올라간다 | 사용자가 아이폰 비행기 모드로 확인했다 |
| 아이폰에서 키보드가 올라와도 `취소`와 `저장`이 보인다 | 사용자가 확인했다 |

- 사용자는 확인 항목 전체에 대해 "다 잘돼"라고 답했다(2026-11-13).
- DesktopCal 기록: 전체 845행 중 빈 칸 56개를 뺀 789일을 옮겼다. 수정 시각 범위는 2023-08-23 ~ 2026-11-13이다.
- 테스트: 단위 178개, 에뮬레이터 12개, 타입 검사 통과.
- Firebase: 무료 요금제(Spark), Firestore 기본 데이터베이스는 서울 리전(`asia-northeast3`), 이메일/비밀번호 로그인, 보안 규칙은 소유자 UID 하나만 읽고 쓴다. 프로젝트 ID와 설정값은 이 PC의 `.env.local`, `.firebaserc`에 있고 git에는 없다.

## 전환 기간에 쓰는 방법

PC 바탕화면 앱(③ 단계)이 나올 때까지 PC에서는 DesktopCal을 계속 쓴다. `npm run import -- --follow`를 PowerShell 창에 켜 두면 DesktopCal에서 고친 내용이 CalendarFIF로 넘어가 아이폰에 보인다. 방향은 DesktopCal → CalendarFIF 한쪽이다. 자세한 사용법은 저장소의 `README.md`에 있다.

## 진행하면서 정한 것

사용자에게 묻지 않고 진행 중에 정한 것을 정한 순서대로 적는다. 틀렸을 때의 비용을 함께 적는다.

1. 워크트리를 따로 만들지 않고 저장소 폴더의 `phase-1-sync-core` 브랜치에서 작업했다. 틀렸다면 나중에 브랜치를 워크트리로 옮기면 된다.
2. 실제 Firebase 프로젝트 연결, 배포, 실제 기록 올리기(Task 13)는 사용자의 프로젝트와 동의가 필요한 일로 보고 Task 12 뒤에 멈춰 물었다. 틀렸다면 잠깐 멈춘 것뿐이다.
3. 도구 버전 때문에 계획의 테스트 코드가 그대로 안 돌 때는 뜻을 바꾸지 않는 가장 작은 수정만 허용하고 보고하게 했다. 틀렸다면 약해진 검증을 검토에서 잡아야 한다.
4. 배포용 규칙 만들기는 `OWNER_UID`가 비었거나 시험용이면 거부하게 했다(Task 4에서 구현). 비용 없음.
5. 문서 형식 변환(`parseMonthDoc`, `buildMonthPatch`)을 한 파일에 모아 웹앱과 가져오기가 같이 쓰게 했다. 틀렸다면 작은 함수 하나가 남는다.
6. 올리기 시작을 아주 잠깐(마이크로태스크 하나) 늦춰 같은 순간에 저장한 편집이 한 번에 올라가게 했다. 틀렸다면 그만큼의 지연이다.
7. 화면 확인용 스크린샷 도구(`scripts/shot.ts`)와 에뮬레이터 전용 자동 로그인을 추가했다. 틀렸다면 개발용 코드가 조금 남는다.
8. 검토 자료에서 `package-lock.json`을 뺐다(최종 검토에서 따로 확인했다). 틀렸다면 잘못된 의존성 항목이 설치 때까지 안 보인다.
9. 완료 표시 버튼이 선택 범위 바로 다음 줄까지 건드리던 문제를 편집 화면 작업(Task 8)에서 고치게 했다. 틀렸다면 몇 줄이다.
10. Task 2 검토가 끝나기 전에 Task 3 구현을 시작했다(서로 다른 파일). 틀렸다면 Task 3을 다시 시험해야 했다.
11. 병합한 글도 저장 규칙(줄 끝 공백과 끝의 빈 줄 정리)을 거치게 했다. 틀렸다면 정리 호출 하나가 더 있다.
12. Task 3 검토가 열려 있는 동안 Task 4 구현을 시작했다(공유 파일 없음). 비용 없음.
13. 대기열 규칙을 좁혔다. 이미 올리기 시작한 편집에는 합치지 않고 뒤에 따로 넣는다. 설계의 목적(편집을 잃지 않는다)이 글자 그대로의 규칙보다 우선한다고 보았다. 틀렸다면 하루에 대기 항목이 여러 개 생기고 코드가 조금 늘어난다. 설계 7.2와 계획을 맞춰 고쳤다.
14. 깨진 대기열 저장소 처리(잘못된 항목 격리, 시작할 때 감지)를 Task 3 수정에 포함했다. 틀렸다면 몇 줄이다.
15. 규칙에 넣는 UID 형식을 영문·숫자·`_`·`-` 1~128자로 정했다. 보안상 비용 없음.
16. 중단된 Task 6의 미완성 파일을 초안으로 보고 새 구현 에이전트가 점검해 마무리하게 했다. 틀렸다면 수정 한 번이 더 든다.
17. 에뮬레이터에 지어낸 예시 메모를 넣게 했다(화면 확인용). 틀렸다면 개발용 코드 몇 줄이다.
18. 가져오기(Task 10~12) 검토를 웹앱 작업과 나란히 진행하고, 병합은 웹앱 구현이 커밋된 뒤에 했다. 비용 없음.
19. 따라가기가 실패한 뒤 파일이 그대로여도 다음 확인 때 다시 시도하게 고쳤다. 틀렸다면 세 줄이다.
20. 같은 날짜가 두 번 나오면 더 늦게 고친 행만 보게 하고, 임시 폴더 정리 실패가 읽은 결과를 버리지 않게 고쳤다. 틀렸다면 몇 줄이다.
21. 한글 조합 중에는 Esc와 Ctrl+Enter를 무시하게 했다. 틀렸다면 몇 줄이다.
22. 전체 검토를 실제 기록을 올리기 전에 했다. 틀렸다면 작은 검토가 한 번 더 든다.
23. 전체 검토에서 나온 것 중 실제 기록을 지키는 것과 작은 것을 한 번에 고치고, 설계 결정이 필요한 것은 미뤘다(아래 "미뤄 둔 것").
24. 설계 7.2를 고쳤다. 대기 중인 편집 위에서 고친 것일 때만 합치고, 아니면 따로 넣는다. 틀렸다면 대기 항목이 늘고, 따로 넣은 두 줄은 나중 편집의 줄이 먼저 온다.
25. 설계 8.4를 고쳤다. 상태 파일이 있으면 거기 없는 날짜는 빈 값에서 고친 것으로 합친다. 처음 가져올 때 건너뛴 날짜는 가져온 것으로 기록하지 않는다. 따라가기는 10일 이상 사라지면 멈춘다. 틀렸다면 PC와 휴대폰이 같은 날짜에 따로 적은 글이 둘 다 남고(사용자가 정리), DesktopCal에서 정말 많이 지운 경우 `--upload --allow-deletes`를 한 번 실행해야 한다.
26. 편집 화면 바깥을 눌렀을 때만 입력한 글을 지켜 주게 했다. Esc, `취소`, 뒤로 가기는 묻지 않고 버린다. 확인 창을 띄울지는 사용자가 정할 일로 남겼다. 틀렸다면 그렇게 닫은 글은 사라진다.
27. 저장한 글이 잠깐 사라져 보이던 문제는 "방금 올린 값을 최대 10초 화면에 유지"하는 방식으로 고쳤다. 틀렸다면 그 10초 동안 다른 기기의 더 새 값이 늦게 보일 수 있다.
28. 아이폰 키보드 대응을 이 PC에서 볼 수 없는 상태로 먼저 구현했다. 사용자가 아이폰에서 확인했다.
29. Task 13 순서를 바꿨다. 가져오기를 먼저 하고, 시험 메모는 그 뒤에 적고, 가져오기 명령은 사용자의 PowerShell에서 실행하고, 배포는 `npm run deploy`로만 한다. 비용 없음.
30. 같은 브라우저의 두 번째 창에서 저장 직후 글자가 잠깐 깜빡이는 문제는 표시만의 문제로 보고 미뤘다.
31. 캐시가 있는 기기에서 읽기 권한 오류가 나면 상태 글자가 2초마다 바뀌는 문제는 규칙을 잘못 배포한 경우에만 생겨서 미뤘다.
32. 올리기가 중간에 실패한 뒤 그 날짜를 DesktopCal에서 고치고 다시 올리면 옛 줄이 함께 남을 수 있다. 코드 대신 안내("실패하면 바로 다시 실행")로 처리했다. 틀렸다면 그 날짜의 옛 줄을 손으로 지워야 한다.
33. Firebase 프로젝트 ID를 `calendarfif`로 정했다(사용자가 "모두 너가 해"라고 한 뒤). ID는 바꿀 수 없다. 주소를 바꾸려면 프로젝트를 새로 만들어야 한다.
34. 계정의 UID는 계정 목록을 저장소 밖 임시 폴더로 내보내 UID만 읽고 그 파일을 바로 지우는 방법으로 가져왔다. 내보낸 파일에는 이메일과 비밀번호 해시가 잠깐 들어 있었다. 남은 비용은 없다. 다른 방법은 사용자가 UID를 직접 복사하는 것이었다.
35. 배포 설정(`firebase.json`)에 기본 데이터베이스와 서울 리전을 적어 넣었다. 설치된 Firebase 도구는 데이터베이스가 없는 프로젝트에 배포하면 데이터베이스를 미국 리전에 만들고, 리전은 바꿀 수 없기 때문이다. 지금 프로젝트에는 영향이 없다.

## 미뤄 둔 것

### 쓰다가 눈에 띌 수 있는 것

- 로그아웃해도 그 브라우저에 달력 캐시가 남는다. 지우면 오프라인 사용과 부딪혀서 결정이 필요하다.
- 날짜 주소로 바로 연 편집 화면을 취소한 뒤 뒤로 가기를 누르면 편집 화면이 다시 열린다. ② 단계(위젯에서 날짜를 눌러 여는 길)를 만들기 전에 고친다.
- 올린 응답을 받지 못한 채 오래 지난 뒤 다시 보낼 때, 그 사이 다른 기기에서 지운 줄이 되살아날 수 있다. 문서에 "적용한 편집" 표시를 넣으면 막을 수 있는데 문서 형식이 바뀐다.
- 첫 화면이 4초 넘게 걸리면 글이 있는 날짜도 편집 화면이 빈 채로 열린다. 저장해도 합쳐지므로 잃지는 않는다.
- 같은 브라우저의 두 번째 창에서 저장 직후 글자가 잠깐 사라졌다 나타난다.
- 다른 기기가 방금 지운 날짜를 다시 만들면 최대 10초 동안 안 보일 수 있다.
- 인터넷은 되는데 권한 말고 다른 이유로 올리기가 실패해도 `오프라인 (대기 n건)`으로 보인다.
- 대기 건수는 날짜 수가 아니라 대기 항목 수라서 하루가 2건으로 보일 수 있다.
- 어두운 화면에서 배경색 `282828`은 거의 안 보인다. 칸 안에서 가운데 빈 줄은 표시되지 않는다.
- `--follow`를 `--upload` 없이 처음 실행하면 대조 보고가 나오지 않고, 10일 삭제 한도가 첫 회부터 적용된다.
- 따라가기는 PowerShell 창을 켜 둔 동안만 돈다. 자동 실행은 만들지 않았다.

### 아직 확인하지 못한 것

- DesktopCal에서 배경색을 "없음"으로 되돌렸을 때 데이터 파일에 무엇이 저장되는지. 실제 데이터에는 빈 값만 있었다. 따라가기를 켠 채 시험 날짜에 색을 넣었다가 지워 보고, 웹앱에서도 색이 사라지는지 보면 된다.
- 아이폰이 홈 화면 웹앱의 저장소를 오래 안 쓰면 비우는 동작(설계 11절의 위험). 비워지면 다시 로그인해야 하고, 올리지 못한 편집이 있었다면 사라진다.

### 코드와 테스트 정리

- 저장소 쓰기 실패 뒤 다시 보내는 경우, 두 탭이 몇 ms 차이로 같은 저장소를 쓰는 경우, 상태 알림을 받는 쪽이 예외를 던지는 경우의 처리.
- 테스트가 없는 곳: 실제 저장소 어댑터의 재시도와 삭제, 다시 구독(지연 늘리기), 가져오기의 따라가기 분기와 실제 로그인, `main.ts`의 연결 코드, 밀어서 달 넘기기.
- 작은 중복과 정리: `isObject` 세 곳, `WIDE_PX` 두 곳, `.env.local` 읽기 두 곳, `visibilitychange`를 `window`에 건 곳, 쓰지 않는 `AppDeps.signOut`, 가져오기 오류 문구에 전체 경로가 들어가는 것, `jdk.ts`의 내려받은 파일 검증.
- README의 "이 명령으로만 배포" 주의는 일부 중복이다(스크립트가 항상 다시 빌드한다).
